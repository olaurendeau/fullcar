Un lieu, une valeur

Un lieu est le couple { text, position }, où position vaut { lat, lng } ou null. Partout où le code compare, envoie, recopie ou vérifie un lieu, il traite ce couple comme une seule valeur, jamais le texte seul.

Comparer

  • Deux lieux sont égaux si leurs textes sont égaux et leurs positions aussi : toutes deux null, ou mêmes lat et lng à 5 décimales.
  • « Valider » sans changement (M2.5, v4.4.5-6) : le lieu compte comme changé si le couple a changé. « Retirer » seul est un changement ; choisir la proposition au texte identique aussi.
  • Modification simultanée (M6.1) : un lieu non touché (couple égal à celui chargé) prend le couple enregistré ; un lieu touché garde le couple saisi, texte et position.
  • « Je ramène aussi » : le lieu de l’autre leg suit le couple entier tant qu’il n’est pas touché.
  • Voiture (v3) : une modification du texte remet la position à null dans le même changement d’état ; le couple change donc d’un coup, texte et position.

« Modifier l’événement » : before et l’envoi

  • EventHeader (et donc before) gagne locationPosition : { title, location, locationPosition, allerAt, retourAt }. sameHeader la compare, sous le verrou, comme le reste.
  • Le formulaire envoie toujours location et locationPosition ensemble.
  • Cas 1 de la revue : A retire la position ; B, ouvert avant, ne change que le titre. Le before de B porte l’ancienne position, la ligne n’en a plus : réponse changed, rien d’écrit ; le lieu de B, non touché, prend le couple enregistré (sans position), son titre reste.
  • Une page chargée avant le déploiement envoie un before sans locationPosition : il est comparé sans la position, et l’écriture garde la position enregistrée, même si le texte change : c’est la règle de l’événement (D6). Expansion, puis contraction dans un déploiement suivant.

« Modifier la voiture » : seulement ce qui change

  • Le lieu est un champ de RIDE_FIELDS : changé (le couple), il part location et position ensemble ; non changé, ni l’un ni l’autre.
  • Cas 2 de la revue : « Mairie, 69670 Vaugneray », sans position, reçoit la proposition au même texte : le lieu a changé, la requête porte location (même texte) et position ; elle est valide.
  • Une page d’avant le déploiement envoie location sans position. Si ce texte est celui enregistré, la position ne change pas. S’il est différent, le serveur met la position à null : un lieu de voiture dont le texte change perd sa position (décision du propriétaire, v3), quelle que soit la page qui l’envoie. Ainsi la position d’une voiture est toujours celle de son texte (AL5.6).

Ce que le serveur refuse (invalid, rien d’écrit)

  • position (ou locationPosition) sans location dans la même requête.
  • Une position qui n’est ni null ni un objet { lat, lng } de deux nombres finis ; une latitude hors de [−90, 90], une longitude hors de [−180, 180].
  • À la création (événement, voiture, autre leg), position absente vaut null.
  • Le serveur arrondit à 5 décimales (environ 1 m) : c’est une mise en forme, pas un floutage (D5 : le point exact).

Ce que reçoit /e/{id}

  • Avec #237 : la position de l’événement (EventHeader.locationPosition) et celle de chaque voiture, dans l’état de la page et dans son actualisation. Les formulaires de modification en ont besoin pour la ligne de position et pour before.
  • Rien d’autre de Photon : ni libellé de la proposition, ni identifiant.
  • Le libellé d’une proposition n’est pas stocké : à l’ouverture d’un formulaire de modification, la ligne dit « Position enregistrée ». Un choix fait dans ce formulaire la remplace par « Position : {libellé} ».

Anatomie et clavier

Le motif : combobox à liste (ARIA 1.2)

  • Le champ garde son <input type="text">, son <label> et sa validation. Il prend role="combobox", aria-autocomplete="list", aria-expanded, aria-controls, et aria-activedescendant quand une option est active.
  • La liste : role="listbox", nommée « Propositions pour {libellé du champ} », rendue dans le formulaire (dans la feuille, pas dans un portail : Radix ne la prend pas pour un clic à l’extérieur). Chaque proposition : role="option" ; l’active a aria-selected="true" et la barre de 3 px. Le pied n’est pas une option.
  • aria-describedby du champ, dans l’ordre : l’erreur, la ligne de position, la phrase de visibilité, celles qui existent.
  • Une région status polie par champ, dans le formulaire (donc dans la feuille, hors du panneau du leg, où getByRole("status") des tests existants n’en voit qu’une), montée vide avec lui : nombre de propositions, « Aucune proposition… », « Propositions indisponibles… » (une fois, voir « Cycle de vie »), « Position ajoutée. », « Position retirée. ». Jamais alert.
  • « Retirer » : un bouton de 44 px, nommé « Retirer la position ({libellé du champ}) ».
  • Aucune dépendance : construit à la main sur le champ shadcn existant.

Clavier et toucher

  • Flèche bas / haut : ouvre la liste si elle a des propositions pour le texte actuel, déplace l’option active ; le focus reste dans le champ.
  • Entrée, la liste ouverte : avec une option active, la choisit ; sans option active, ferme la liste et n’envoie pas le formulaire. La liste fermée, Entrée garde son effet d’aujourd’hui.
  • Échap, la liste ouverte : ferme la liste seule et garde le texte. Dans une feuille, l’onEscapeKeyDown de la feuille appelle preventDefault() tant qu’une liste est ouverte. La liste fermée, Échap ferme la feuille comme aujourd’hui.
  • Tab, ou un tap ailleurs : ferme la liste, garde le texte, ne choisit rien.
  • Un tap sur une option la choisit ; options de 44 px au moins.
  • Sans JavaScript : sans objet, les formulaires de création et de voiture le demandent déjà.

Quand une requête part

  • Au moins 3 caractères après trim, et au plus 120.
  • 300 ms après la dernière frappe ; une seule requête en cours par champ (la précédente est abandonnée par AbortController), et une réponse pour un autre texte que le texte actuel est ignorée.
  • Jamais à l’ouverture d’un formulaire, ni au focus, ni pour un texte égal au libellé qui vient d’être choisi, ni pendant l’envoi du formulaire.
  • Navigateur hors ligne (navigator.onLine faux) : aucune requête, la ligne « indisponibles » après la pause.
  • 3 s sans réponse : la requête est abandonnée, « indisponibles ».

Le libellé d’une proposition

  • Un lieu nommé : « {nom}, {code postal} {commune} ».
  • Une adresse : « {numéro} {rue}, {code postal} {commune} ».
  • Une rue : « {rue}, {code postal} {commune} ».
  • Une commune : « {commune} ({code postal}) », sans code postal « {commune}, {département ou région} ».
  • Hors de France : « , {pays} » à la fin, dans la langue de la page.
  • Deux libellés identiques : un seul. Plus de 120 caractères : pas montré.

La route /api/lieux et Photon

La route (décision du coordinateur)

  1. POST /api/lieux, un route handler de notre origine (src/app/api/lieux/route.ts). Pas une server action : Next exécute celles d’une page une à une, et une réponse lente de Photon retarderait l’envoi d’un formulaire ou l’actualisation de 15 s (loadEventState), ou serait retardée par elles au point de dépasser 3 s.
  2. Corps JSON : { "text": "…", "locale": "fr" | "en", "near"?: { "lat": n, "lng": n } }, 1 Ko au plus. Le texte n’est jamais dans une URL de notre origine.
  3. Refus sans appel à Photon : autre méthode (405) ; Origin absent ou autre que notre origine (403) ; corps illisible, trop gros, texte de moins de 3 ou de plus de 120 caractères après trim, locale inconnue, near hors bornes (400, { "state": "invalid" }).
  4. Réponse 200, Cache-Control: no-store : { "state": "ok", "suggestions": [{ "label", "lat", "lng" }] } (0 à 5) ou { "state": "unavailable" }. Jamais le détail d’une erreur.
  5. Vers Photon : GET https://photon.komoot.io/api/?q=…&limit=5&lang=…, et pour un champ de voiture &lat=…&lon=… : la position de l’événement arrondie à 1 décimale (environ 10 km), jamais la position exacte. L’URL de Photon vient d’une variable d’environnement.

Ce que Photon voit, et ce qu’il ne voit pas

  • Voit : le texte tapé, la langue, pour un champ de voiture la zone de l’événement à 10 km près, l’IP de Vercel, notre User-Agent.
  • Ne voit pas : l’IP du visiteur (aucun X-Forwarded-For, X-Real-IP, Forwarded), son User-Agent, ses cookies, un Referer, la position exacte de l’événement, son identifiant, un jeton, un prénom.
  • Nous ne journalisons ni le texte ni la réponse. Un échec journalise un message fixe et le statut HTTP de Photon, rien d’autre.
  • Sentry : l’URL sortante vers Photon porte q=. Ni un fil d’Ariane, ni un span, ni un rapport d’erreur ne la garde avec sa query : le hook de scrub.ts retire la query de toute URL sortante (data.url, http.query, url.query, url.full), et l’erreur levée sur un échec de Photon ne porte pas l’URL. Côté navigateur, le fil d’Ariane du fetch vers /api/lieux n’a que l’URL et le statut, jamais le corps.

Rester un bon citoyen de l’instance publique

  • Côté navigateur : 3 caractères, 300 ms, une requête à la fois, 5 résultats.
  • User-Agent descriptif : fullcar/{version} (+https://github.com/olaurendeau/fullcar). Pas d’adresse e-mail : au propriétaire d’en ajouter une s’il le veut.
  • Cache en mémoire de l’instance : 500 entrées, 1 h, clé = texte normalisé (minuscules, espaces réduits) + langue + near arrondi (1 décimale). Jamais écrit en base ni sur disque.
  • Disjoncteur par instance : après un 429, un 5xx ou 3 s sans réponse, aucun appel pendant 60 s (ou la durée de Retry-After) ; la route répond aussitôt unavailable. Durée lue dans PLACES_BREAKER_MS (60 000 par défaut).
  • Plafond par instance : 5 appels par seconde ; au-delà, unavailable sans appel.

Ce qui est stocké

  • event.location_lat, event.location_lng, ride.location_lat, ride.location_lng : double precision, nullables, les deux ou aucun (check), latitude dans [−90, 90], longitude dans [−180, 180], arrondies à 5 décimales.
  • Renseignées seulement quand une proposition a été choisie. Ni identifiant Photon, ni libellé, ni réponse.
  • Mêmes lignes que le lieu : la purge les emporte. Migration par expansion.
  • Le serveur ne vérifie pas que la position correspond au texte : il ne le peut pas, et ce n’est pas une règle.
Tests. Aucun test ne joint Photon.
  • Vitest : le disjoncteur (AL2.5), le plafond, le cache et le délai de 3 s sont testés sur le module de la route, avec une horloge et un fetch injectés ; le libellé et l’arrondi de near sont des fonctions pures du domaine ; le retrait de la query par scrub.ts (AL6.6) aussi.
  • Bout en bout : PHOTON_URL pointe vers un faux Photon du slot, ajouté à compose.yaml (PR mergée par l’humain). Il répond vide par défaut, si bien que les tests existants (AL2.4) passent sans changement ; un test qui veut des propositions, un 500, un 429 ou de la lenteur le règle pour son texte, sur le port de contrôle du faux service (pas une route de notre application). Il enregistre chaque requête reçue, en-têtes compris. Dans le slot de bout en bout, PLACES_BREAKER_MS=0 : un test qui provoque un 429 n’ouvre pas le disjoncteur pour les tests parallèles ; le disjoncteur lui-même est prouvé par Vitest.

Décisions

  1. D2–D6 (propriétaire). Photon public, par notre serveur ; latitude et longitude stockées seulement après un choix ; point exact, voitures comprises ; position gardée après modification du texte, sur sa ligne, avec « Retirer » — pour le lieu de l’événement seulement.
  2. Propriétaire (v3). Pour le lieu d’une voiture, toute modification du texte après un choix retire la position. — Raison : une personne qui réduit son adresse à sa commune ne doit pas rester épinglée chez elle pour tout porteur du lien. Conséquence : la position d’une voiture est toujours celle de son texte, et la carte (#238) ne montre jamais un point que le texte ne dit pas.
  3. D9 (propriétaire). « position » entre au glossaire : les coordonnées d’un lieu, quand il a été choisi parmi les propositions. PR de documentation, mergée par l’humain.
  4. Coordinateur (revue v1). Une route POST /api/lieux, pas une server action ; la position de l’événement envoyée à Photon arrondie à 1 décimale.
  5. Décision : un lieu est une seule valeur { text, position } pour comparer, envoyer, recopier et vérifier ; before de « Modifier l’événement » porte la position. — Raison : revue de la v1, bloquant 1 ; sans cela, une modification du titre réécrit une position retirée ailleurs, et un choix au même texte part sans texte.
  6. Décision : une frappe ferme la liste ; la nouvelle arrive avec la réponse. — Raison : une liste pour un texte qui a changé ne doit pas être choisie (revue, bloquant 6) ; une liste grisée mais visible serait une règle de plus pour le même résultat.
  7. Décision : « Recherche de propositions… » après 1 s seulement, jamais annoncée. — Raison : une réponse rapide ne fait rien clignoter ; une attente longue est dite ; un lecteur d’écran n’a pas à entendre chaque attente.
  8. Décision : « indisponibles » annoncé une fois tant que le focus reste dans le champ. — Raison : avec le disjoncteur ouvert, chaque pause donnerait la même annonce ; l’écran la montre toujours.
  9. Décision : Échap ferme la liste avant la feuille. — Raison : revue, bloquant 3 ; dans « Modifier l’événement », Échap vaut « Annuler » et perdrait la saisie.
  10. Décision : pendant l’envoi, le champ ne propose rien et « Retirer » ne fait rien, dans les quatre formulaires. — Raison : décision 52 d’organizer-view, étendue au lieu ; une seule règle pour les quatre.
  11. Décision : la phrase de visibilité sous chaque lieu d’une voiture, toujours affichée. — Raison : demande du propriétaire avec D5 ; aucune phrase existante ne le dit.
  12. Décision : pas de phrase sous le lieu de l’événement. — Raison : il est fait pour être vu par le groupe.
  13. Décision : la ligne de position dit « Position : {libellé} » après un choix, et « Position enregistrée » à l’ouverture d’un formulaire de modification. — Raison : le libellé n’est pas stocké (D4 : rien d’autre de Photon) ; répéter le texte du lieu ne dirait rien.
  14. Décision : un seul message pour hors ligne, panne, lenteur, limitation et disjoncteur. — Raison : la personne fait la même chose dans tous les cas.
  15. Décision : pays en fin de libellé hors de France seulement. — Raison : le cas courant reste court à 360 px.
  16. Décision : cache en mémoire seulement. — Raison : une table de cache stockerait des textes tapés, souvent des adresses.
  17. Décision : /api/lieux refuse un Origin qui n’est pas le nôtre. — Raison : la route ne doit pas servir de proxy Photon gratuit à d’autres sites ; un client hors navigateur peut forger l’en-tête, le plafond de 5 appels par seconde protège Photon dans ce cas.
  18. Décision : la durée du disjoncteur vient de PLACES_BREAKER_MS, 0 dans le slot de bout en bout. — Raison : tests parallèles indépendants sans route réservée aux tests ; le disjoncteur est prouvé par Vitest.

Hors périmètre

  • Les lieux des Arrêts (la table n’existe pas encore) : quand elle arrive, elle reprend ce champ.
  • « Autour de moi » et toute géolocalisation de l’appareil.
  • Rattacher une position aux lieux saisis avant #237.
  • Un lien « Ouvrir dans mon GPS » sur le lieu : une issue à part.
  • Choisir ou corriger la position en touchant une carte.
  • Une instance Photon à nous (environ 95 Go pour le monde) : une décision d’hébergement.
  • Sans JavaScript : sans objet, les formulaires concernés le demandent déjà.
